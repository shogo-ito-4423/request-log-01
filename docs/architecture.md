# 設計判断 — 1日版

## 解決する課題

改善要望が会話やメモに散らばると、担当と進捗を追跡できない。
要望を1件ずつ登録し、優先度・担当者・状態を更新できるAPIを最小単位として実装する。
実際の業務データは使わず、デモ用の架空の要望で検証する。

## データモデル

issuesテーブルの主キーは整数ID。title、description、status、priority、assignee、
created_at、updated_atを持つ。1日版では担当者を文字列で扱い、ユーザーテーブルを作らない。
状態・優先度はAPIの列挙型とDBのCHECK制約で制限する。
日時はUTCで書き込み、SQLiteから返るタイムゾーンなしの値にも出力時にUTCを付与する。

## 主な判断とトレードオフ

| 判断 | 理由 | 制約と次の対応 |
|---|---|---|
| SQLite | 外部DBサーバー不要で永続化を実証できる | 多数の同時書き込みには不向き。次版でPostgreSQLを検証 |
| 同期SQLAlchemy Session | 小規模APIで処理とトランザクションの境界が明確 | 非同期化は負荷測定後に判断 |
| 起動時create_all | 初期構築を単純にする | スキーマ変更の履歴管理はAlembicで追加 |
| PATCH + exclude_unset | 未指定フィールドを意図せず消さない | nullと省略の意味をテストで固定 |
| ID昇順 + limit/offset | 再現性のある有限件数の一覧 | 大量データではカーソル方式を検討 |
| 自動リトライなし | 現段階で複雑な再試行や二重登録を持ち込まない | 同時書き込み時のエラー設計は後続版 |
| ローカル専用公開 | 認証未実装のデモをLANに公開しない | 外部公開前に認証・認可・TLSを追加 |

## トランザクションとエラー

1リクエストに1Sessionを用意する。書き込みは1回のcommitで確定し、終了時にSessionを閉じる。
入力検証は書き込み前に実行し、不正なPATCHで既存レコードを変更しない。
未存在は404、入力不備は422、ヘルスチェックのDB接続エラーは503。
想定外のDB書き込み失敗は500となる。API利用者へ接続の内部情報を返す独自処理は加えない。

## 検証の層

pytestでは一時ファイルのSQLiteを使い、HTTPレベルの契約と実DB保存をまとめて検証する。
モックだけでは永続化の不備を発見できないため、DB障害テスト以外は実DBを使用する。
さらに実行イメージの非rootユーザーで作成・取得・更新できることと、
コンテナを再作成しても名前付きボリューム上のレコードが残ることをスモークテストで検証する。

## 次の小さなIssue

1. PostgreSQLとAlembicを導入し、既存データを保持した移行手順を検証する。
2. status / priority検索を追加し、必要なインデックスを測定して決める。
3. 認証・認可を追加し、公開可能な範囲と運用方針を定義する。

面接では「SQLiteで初日を完結させた理由」「PATCHのnullと省略の違い」
「CIでコンテナ再作成まで検証する理由」を、コードとテストに対応させて説明できる。
