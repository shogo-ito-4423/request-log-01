# C1 認証・認可

## 合意した操作範囲

| 操作 | 一般利用者 | 管理担当者 |
|---|---|---|
| 登録 | 自分の要望として登録 | 自分の要望として登録 |
| 一覧・詳細 | 全員の要望 | 全員の要望 |
| 更新・削除 | 自分の要望だけ | 全員の要望 |

管理担当者の全操作は既存CRUDを意味し、他人への所有権移譲は対象外。
`owner_id` は認証した利用者IDをサーバーが設定する。担当者の表示名 `assignee` とは別物。
入力で所有者・権限を指定すると422。一般利用者が他人の要望を変更すると403。
未認証・無効トークンは401と `WWW-Authenticate: Bearer`。認証済みで未存在のIDは404。
`/health`・`/docs`・`/openapi.json` は公開し、要望データは返さない。

## 方式・設定

小規模な招待利用を想定し、利用者ごとの不透明なランダムBearerトークンを採用した。
サーバー設定 `AUTH_USERS_JSON` は `user_id`・`role`（user/admin）・`token_sha256` の配列。
SHA-256ハッシュを定数時間比較し、役割はサーバー設定だけから取得する。
これはパスワード保存方式ではない。32バイト以上の安全な乱数からトークンを生成する。
空・不正設定、利用者IDやハッシュの重複は起動エラーにし、匿名アクセスへ切り替えない。

READMEの `scripts/create_local_auth.py` はコンテナ内で `.env` を新規作成する。
既存ファイルは上書きせず、0600で保存する。`.env` はGit除外済み。
ローカルデモでは配布・検証用に生トークンも保存する。`API_TOKEN` はスモーク試験の
クライアント用であり、認証サーバーが照合に使用する値ではない。
ホストへの環境変数設定は不要で、Composeがリポジトリの `.env` を読み込む。
テストは架空の固定トークンをfixtureで設定し、CIの実HTTP検証は実行ごとに乱数を生成する。

利用者を追加するときは一意で安定したIDと新しいトークンハッシュを設定する。
IDを他人に再利用すると過去の要望を操作できるため、再利用しない。
ローテーションでは同じ利用者IDのハッシュを置換し、全APIインスタンスを再作成する。
失効は該当利用者を設定から削除して全インスタンスを再作成する。反映まで旧トークンは有効。
トークンをGit・URL・ログに記載せず、本人へ安全な経路で配布する。

公開環境ではHTTPSと秘密管理サービスを用い、生トークンをAPIコンテナの設定に置かない。
ログイン画面・自己登録・自動期限切れ・即時失効・監査ログは未実装。
OIDC等はこれらを外部IdPへ委ねられるが、今回は外部利用の設定を必要としない最小構成とした。
公開先と秘密管理・TLSの実検証はC2で行う。C1完了だけで公開済み・運用検証済みとは扱わない。

## DB移行

Alembic `0002` は既存行を保持してNULL許可の `owner_id` を追加する。
既存行はNULLのままとし、推測で誰かの所有物にしない。閲覧は全利用者、変更は管理担当者のみ。
既存revision 0001適用済みDBはバックアップ後、APIを止めて `alembic upgrade head` を実行する。
API再開前に `alembic current` が0002であることと動作を確認する。
`downgrade 0001` は要望本体を保持するが所有者情報を失う。再upgradeでも所有者は戻らない。
運用の復旧にはバックアップ復元や前進修正を検討し、機械的にdowngradeしない。
