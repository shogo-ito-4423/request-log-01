# C2：デモ公開の費用・運用・検証計画

2026-11-10設計版。[構成・認証設計](issue-cloud-design.md)と併せてレビューする。
以下はこれから実装・検証する手順であり、配備済みの手順書・検証結果ではない。
運用責任者はリポジトリ所有者。Codexは承認された範囲で作業を補助する。

## リソースと費用

専用Google Cloudプロジェクトにus-west1のe2-micro 1台、固定IPv4 1個、標準永続ディスク
合計30GB、VPC・ファイアウォール、非公開Artifact Registry 1個、非公開Standardバケット1個、
Secret Manager設定束5個（ローテーション・予備込み12版以内）、必要なIAMを作る。
ロードバランサー・Cloud NAT・Cloud SQL・有料サポート・ドメイン購入は使わない。
作成・公開は別途承認後。既存プロジェクトの共有資源を流用・変更しない。

### 月額試算

公式料金確認日2026-11-10。31日＝744時間で計算する。VM・ディスクのみ無料枠を必須とし、
他は利用可能な無料枠を控除せず保守的に計上。主に日本へ配信、送信1GiB/月以下、デモデータのみ。

| 項目 | 数量・計算 | USD/月 |
|---|---|---:|
| VM・標準ディスク | e2-micro 744時間、30GB月以内、既存利用との合算で無料枠内 | 0.00 |
| 使用中IPv4 | 744 × $0.005 | 3.72 |
| イメージ | 2GiB × $0.10、無料0.5GiBを控除しない | 0.20 |
| バックアップ | 2GiB × $0.02、Standard・同一リージョン | 0.04 |
| バックアップ操作 | Class A 1,000回、Class B 10,000回以下の予備枠 | 0.01 |
| 外向き通信 | 日本向け1GiB × $0.12、無料枠を控除しない | 0.12 |
| 秘密の版 | 12active versions × $0.06、1ロケーション | 0.72 |
| 秘密取得 | 10,000操作、無料枠を控除しない | 0.03 |
| ログ | 0.5GiB × $0.50、30日以内、無料枠を控除しない | 0.25 |
| **合計** | 上記の利用量以内 | **5.09** |

計画値として1ドル160円・税等の予備係数1.10なら約896円/月、予算まで約104円。
これは現在の為替や実税率・請求レートではない。配備前に実請求通貨のSKUと契約条件で
再計算し、900円を超える見通しなら配備を保留する。初期作成そのもののセットアップ料は
見込まず、初回イメージ・バックアップ・証明書検証も上記数量内に収める。
既存GitHub Actionsの利用可能枠を確認し、枠外料金があれば1,000円へ加算する。

イメージpull・バックアップは同一リージョン。有料スキャン、クロスリージョン転送、長期ログ、
管理用別VM、ディスクsnapshotは含めず、無断で有効化しない。無料枠の既存消費・地域・
ディスク種別が異なれば試算は無効。保持量には旧世代・soft delete分も含める。

### 予算・停止判断

月1,000円の予算通知を責任者へ設定。500円で確認、700円または月末予測900円で新規招待を停止。
800円到達または900円超予測が解消しなければ公開停止・撤収を判断する。7日でデモ操作を停止し、
延長指示がなければ翌日リソース・費用をレビューする。保管データを無断削除しない。
送信1GiB・保管量・版数・ログ量を日次確認する。

通常の予算通知は請求遅延があり課金上限ではない。[予算仕様](https://docs.cloud.google.com/billing/docs/how-to/budgets)
API上限も未認証通信・固定費を止めない。異常アクセスは入口の頻度制限と小さい拒否応答で抑え、
継続なら公開を閉じる。1,000円を数学的に保証する方式ではなく、超過不可が厳格な契約条件なら
公開クラウド案を再検討する。

## 起動・移行・更新

運用者がIAP/OS Loginで対象VMを確認し実施。プログラム・クラウドCLIはコンテナ内、
サービス管理はCompose。アプリ起動時に自動移行せず、移行は1ジョブに限定する。

1. Git SHA、digest、予定revision、設定version、予算確認結果を記録する。
   初回は専用の空DB。既存ローカルSQLite/PostgreSQLは移送しない。
2. 再配備では入口をメンテナンス状態にし、新しい操作と招待交換を停止。
   実行中要求を完了させ、アプリの書き込み停止を確認する。
3. 既存DBのpg_dumpとロール再作成用定義を取得し、ハッシュ・revision・SHA・時刻を記録。
   秘密を含む情報は非公開バックアップとして扱う。
4. DB health後、一時移行コンテナだけにmigration資格を渡し `alembic upgrade head` を実行。
   `alembic current`、期待revision、制約、GRANT、既存行を確認する。
5. 失敗時は新API/画面を起動せず、入口を閉じたまま部分適用の有無とログを調べる。
6. 成功時はdigest固定でAPI/画面を起動し、内部health・権限・HTTPSスモーク後に公開を再開。
   失敗なら閉じたまま復旧する。手順を実装時の配備スクリプトへ落とし込む。

## バックアップ・復旧

日次と配備前に互換バージョンのpg_dumpをコンテナ内で実行。issuesと招待・セッション・
回数を同じDBの整合したsnapshotで保存し、非公開バケットへ格納する。
DBディスクから分離し、復旧担当だけが読める権限にする。作成処理に削除・公開権限を与えない。
7日分・総量2GiB以内を目標とし、旧世代・soft deleteも監視。期限超過分の削除や
ライフサイクル設定は配備時に対象と期間を示して承認を得る。
RPOは24時間以内、RTOは2時間を目標とするが、復元演習までは未検証。

1. 入口と書き込みを停止し、現状のDB・ログを保持する。
2. 旧APIと現スキーマに互換性があれば正常digestへ戻して内部health/CRUDを検証する。
3. 非互換なら機械的なdowngradeを避け、前進修正か復元を判断する。復元は別DB／
   専用ボリュームへ行い元DBを上書きしない。追加容量・費用も確認する。
4. revision、件数、代表行の全項目・所有者を比較し、旧版の内部HTTP試験を実行。
5. 古いバックアップは使用済み招待・少ない回数を含み得る。復元した招待・sessionを
   すべて失効し、回数は信用できる現行値と比較して大きい値を採用する。
   比較できなければ期間を停止し、再発行で枠を復活させない。
6. 責任者がデータ差分とアクセス制御を確認して再開する。失われ得る更新を記録し、
   復旧用資源の撤収は対象確認・承認後に行う。

## 招待配布・失効

管理コンテナがcampaignと利用者を作り、既存APIの安定したuser_idへ対応付ける。
秘密は引数・標準ログへ出さず、管理者だけが読める一時ファイルに発行する。
責任者が利用者へ個別配布する。Issue・PR等の共有場所へ貼らず、Codexが勝手に送信しない。
再発行は旧招待・全sessionの失効と新招待作成を1トランザクションで行い、期限・回数は維持。
失効後の旧Cookie拒否を確認する。既に許可・転送した要求の取り消しは保証しない。
内部APIトークン漏洩時はSecret Managerの新versionへ更新し、メンテナンス中にAPI/画面を
再作成する。新資格成功・旧資格401を内部試験して再開する。

## 停止・撤収

一時停止：招待・sessionを無効化し入口を閉じ、API/画面を停止。DBとバックアップは保持。
VM停止だけでも固定IP・保存資源の料金が残り得ることを記録する。
恒久撤収：対象プロジェクト・資源一覧、最終バックアップ、保持期限、削除対象・費用を提示。
承認後にVM・IP・専用ルール等を撤収し、不要IAM/OIDC権限を解除する。
ディスク・ボリューム・バックアップ・秘密版・復旧イメージは明示的な削除承認があるものだけ削除。
広範囲pruneやプロジェクト丸ごとの無確認削除はしない。保持資源と費用を台帳へ残し、
翌日の一覧・請求で残存課金を確認する。

## 受入検証計画

全項目は未実行。専用の架空データで、日時・SHA/digest・revision・実測を残す。
URL秘密・Cookie・DB接続文字列は証跡から除外する。失敗項目があれば公開しない。

| ID | 手順 | 期待結果 |
|---|---|---|
| V1 TLS | 外部の検証コンテナからIPのHTTPSへ接続、SAN・発行者・期限確認。HTTPも要求 | 信頼済みIP証明書、HTTPはHTTPSへ転送、アプリ操作不可 |
| V2 更新 | stagingで取得→更新→reload。本番更新予定・6時間ジョブ・期限通知を確認 | 更新証明書が配信される。更新失敗時は壊れた証明書へ切替えず通知 |
| V3 境界 | 外部から8000/5432/22に接続。入口へ/issues・/docs・/openapi.json・/healthを要求 | 直通不可、API応答・仕様・DB情報を取得不可。IAP管理接続は成功 |
| V4 health | 内部/health、検証用DB停止後に再要求しDB復帰 | 200→503→200。外部へhealth公開なし |
| V5 招待 | 初回・再利用・無効・期限切れ・同時2件の交換 | 初回のみ成功、同時成功1件、他401。Cookie属性が設計どおり |
| V6 再発行 | 操作後に再発行、旧URL・旧Cookie・新URLを試す | 旧資格拒否、新URLのみ交換可、期限・回数不変 |
| V7 CRUD | Aで登録→一覧/詳細→更新、BでAの変更/削除、Aで削除。内部管理権限も確認 | 201/200/200、Bは403、Aの削除204、後続404。owner偽装不可 |
| V8 枠 | 99回から2回、全体枠上限、残り1回への並列要求 | 100回成功、101回429。拒否時の転送0、成功数が残枠以下 |
| V9 障害 | 枠DB障害、内部APIタイムアウト、commit直後停止 | DB障害503・転送0。転送失敗/commit後停止は1回消費、自動再試行なし |
| V10 永続化 | 行・所有者・回数を記録しAPI/画面/DB再作成、VM再起動後にも照合 | ID・全項目・回数保持、期限延長なし |
| V11 権限 | Origin/CSRF不正、禁止表/DDL操作、appからmetadataへ要求。ログ検査 | 状態変更・禁止DB操作・metadataを拒否。秘密が画面・ログにない |
| V12 移行復旧 | 旧revisionにデータ→upgrade、移行失敗注入、別DBへdump復元 | 旧行保持、失敗時公開再開なし、復元一致、旧資格失効・枠復活なし |
| V13 負荷 | 検証用期間で10並列の小さいCRUD、メモリ・容量・遅延を計測 | OOM・意図しない5xxなし、目安p95 3秒以内。不足なら再設計 |
| V14 停止費用 | 期限終了と予算通知を試し、公開停止、資源一覧と見積もりを照合 | 期限後操作不可、責任者へ通知、保持資源・残額を一覧化 |

インフラ試験は配備承認後。アプリ・DB並列試験は先にDocker内で行いCIへ組み込む。
本番証明書の自然更新が初回公開まで未到来なら、staging成功と本番設定確認を区別して記録し、
最初の本番更新を責任者が確認する。未実施を「本番更新成功」としない。

## 配備前の確認条件

実アカウントは未検証。以下の担当・確認結果を配備記録に残す。

| 条件 | 担当・確認方法 | 不成立時 |
|---|---|---|
| 無料枠・請求 | 責任者がBillingと全対象プロジェクトの利用量を照合。実通貨で900円以内の見通しを記録 | 配備保留・再見積もり |
| 権限・API | 責任者が専用プロジェクト・請求関連付け、Compute/IAP/OS Login/Secret/Registry/Storageの権限と利用条件を確認 | 最小権限を整理。Owner常用で代替しない |
| イメージ | Codexが保守版・digest・amd64・保管量を確認し、取得対象を提示 | 対応版・費用を見直す |
| 手順実装 | CodexがC2a〜d、設定読込、Compose、移行・backup・TLSジョブを検証し、責任者が証跡レビュー | 修正完了まで非公開 |
| 予算・削除 | 責任者が費用・通知先・公開範囲・保管期限・削除対象を確認 | 作成・公開・削除を保留 |
| 配備承認 | 作成物・費用・公開範囲・停止手順を一括提示し責任者が明示承認 | 課金リソースを作成しない |

これは実装後・配備直前の確認条件であり、今回の設計文書コミットにクラウド認証情報は不要。
