# C2a：デモAPIの呼び出し回数を永続的に制限する

対象M3。ローカル候補C2a、GitHub未起票。依存C1（#22、完了）とC2前半の設計。
2026-11-10作成。見積もり60〜90分、実績未計測。

## 背景・解決する問題

10名に利用者別URLを配り、非公開APIを画面経由でデモ操作できるようにする。
利用者は「HTTPリクエストを画面から迂回して送信された場合、呼び出し回数を
制御できない」と説明した。画面だけの制限を避けるため、API転送前にサーバー側で
利用枠を消費する仕組みを作る。まずDB上の利用枠とその検証を独立した課題にする。

## 範囲・実装方針

画面サーバーから呼ぶ利用枠サービスとモデル・移行・テストを追加する。
既存APIへ制限を適用するのはC2cの転送処理で行う。この課題だけでは公開デモや
既存APIの回数制限は完成しない。

- デモ期間を表すcampaignと、campaign内の利用者枠を作る。
  campaignは全体上限・使用回数・期限・有効状態を持ち、利用者枠は安定したuser_id、
  個別上限・使用回数・有効状態を持つ。campaign/user_idは一意。
- 上限は正の整数、使用回数は0以上かつ上限以下というDB制約を付ける。
  APIリクエストやブラウザから上限・user_idを指定させない。
- 初期設計値は100回/人、1,000回/期間、期間開始から7日間。設定値として扱い、固定値を
  実装に埋め込まない。招待・セッションも同じ期間終了で失効し、再発行で延長しない。
- 消費処理はサーバーで確定したcampaignとuser_idを受け取り、全体枠→個別枠の順に
  `used < limit` 等の条件付きUPDATEを行う。両方成功した場合だけcommitする。
  個別枠の失敗時には全体枠の更新もrollbackする。
- DBのUPDATE件数で成功を判定し、SELECTで残数を読んでから無条件UPDATEする実装を避ける。
  PostgreSQLで同時要求を検証する。SQLiteも既存テスト環境として維持する。
- 期限切れ・無効・枠なし・上限到達・DB障害を呼び出し元が区別できる結果として扱う。
  HTTPステータスへの変換とAPI転送はC2c。障害時に許可扱いへ切り替えない。
- commit完了後にだけ内部APIを呼ぶ契約とする。消費後の転送失敗・タイムアウトでは返却しない。
  自動再試行で呼び出し回数を増やさない。
- URL再発行ではcampaign/user_idを変えないため、回数を初期化しない。
  利用者の無効化も回数を消さない。次のデモ期間は明示的な新campaignで分ける。

## 検証可能な完了条件

- [ ] Alembicの次revisionで利用枠テーブルを追加し、既存issuesの全データを保持する。
- [ ] 使用回数・上限のDB制約とcampaign/user_idの一意性を検証する。
- [ ] 100回目は成功し101回目は拒否、拒否時は両方の使用回数が変わらない。
- [ ] 個別枠に余裕があっても全体上限なら拒否する。
- [ ] 個別枠が上限なら全体枠だけを消費しない。
- [ ] 別利用者の個別枠は独立し、全体枠だけを共有する。
- [ ] 期限と一致する時刻を含む期限切れ・無効・枠なしを拒否する。
- [ ] アプリ／DB接続の再作成でも回数が保持される。
- [ ] 専用PostgreSQLで残り1回への並列要求を実行し、成功が厳密に1回である。
      同一利用者と、異なる利用者による全体枠競合の両方を検証する。
- [ ] DB障害・個別枠更新失敗時に、許可結果や片側だけの消費を残さない。
- [ ] 既存API・認可・移行試験、RuffをDocker内で実行して成功する。

## 変更箇所・実行方法

- `app/models.py`：campaign・利用者枠のモデルと制約。
- `app/demo_quota.py`（新規）：利用枠消費と判定結果。
- `migrations/versions/0003_*.py`（新規）：既存issuesを変更しない追加移行。
- `tests/test_demo_quota.py`（新規）：境界値・rollback・保持・期限。
- PostgreSQL専用テスト：専用の空DB・独立Sessionで並列更新を確認。
- `tests/test_migrations.py`：現在のhead `0002` の期待値と新テーブルの照合を更新。
- 専用Compose・CI：既存の移行用／CRUD用DBと干渉しない並列試験の実行方法を追加。
  既存の通常テストが実DB接続を要求しない構成を維持する。

既存のDocker/Compose手順を使用し、新規検証ボリュームは保持する。
専用DBは未使用であることを確認してから作成し、既存データで並列試験を行わない。
新規イメージ取得が必要なら取得前に確認する。

## 必要な概念・レビュー観点

SQLAlchemy、トランザクションの原子性、条件付きUPDATE、DB制約、Alembic、pytest、
PostgreSQLでの並列検証。2つのカウンターが一緒に確定・取り消される理由と、
ローカル成功・CI成功・配信先での成功の違いを説明できることを確認する。
