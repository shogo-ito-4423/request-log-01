# B5：PostgreSQLの全CRUD・マイグレーション検証をCIへ組み込む

対象はM2。依存するB3（Issue #14）・B4（Issue #17）は完了。見積もりは60〜90分（CI待ち時間や理解度確認によって継続する）。GitHub未起票。

## 背景・解決する問題

PostgreSQLへの実接続とAlembicの移行往復はローカルで検証済みだが、現在のCIはSQLite中心である。PostgreSQLでの全CRUDと移行を継続的に検証できず、DB固有の不具合を変更時に検出できない。

## 実装内容案

- PostgreSQL用Composeを使い、既存データと分離した検証DBで全CRUDの統合テストを実行する。
- 既存の移行往復テストを専用の空PostgreSQL DBで実行し、CRUD試験とデータが干渉しない構成にする。
- GitHub Actionsに上記の検証を組み込み、既存のSQLite・単体テスト・Ruff・永続化検証を維持する。
- README、開発手順、設計資料に実行方法・検証範囲・DB分離の理由を反映する。

具体的なテスト構成は利用者と設計方針を検討してから決める。

## 完了条件

- PostgreSQLで登録・一覧・詳細取得・更新・削除の一連の操作を検証し、応答コードと保存内容を照合する。
- 未存在・再削除の404、不正入力の422、更新失敗時のデータ保持、削除後の取得不可と他レコード保持を検証する。
- 専用の空PostgreSQL DBでupgrade→downgrade→upgradeを検証し、revision・モデルとの整合・CHECK制約・移行後の登録取得を確認する。
- CRUDと移行のテストは既存DB・互いのデータに依存せず実行できる。ローカルの既存ボリュームや永続データは削除しない。
- アプリと検証をDocker内で実行し、既存・追加のテスト、Ruffの静的解析・整形チェックが成功する。
- GitHub Actions上でPostgreSQLのCRUD・移行検証と既存チェックが成功する。失敗時にログを確認できる。
- README／開発手順／設計資料のコマンドでローカル検証を再現でき、Issue・PR・CIの実際の証跡を台帳へ記録する。ローカル成功とCI成功・マージは区別する。

使用する概念・ツールはGitHub Actions、Docker Compose、PostgreSQL、pytest、Alembic、テスト用DBの分離、単体テストと統合テストの役割分担。

クラウド公開、認証・認可、SQLiteからPostgreSQLへの既存データ移送、追加検索・性能改善は対象外。
